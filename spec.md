# Дежурный по дедлайнам: спецификация текущего этапа

## Назначение и границы

Сервис рассчитан на одного пользователя. Основной сценарий: создать дедлайн, получить список актуальных сроков и отметить выполненное. Данные хранятся в SQLite и сохраняются после перезапуска. Аутентификация, уведомления и контейнеры в текущий этап не входят.

Ниже зафиксировано поведение существующих маршрутов. Оно описывает стартовую версию и не разрешает добавлять возможности следующих этапов без новых требований.

## Данные дедлайна

Дедлайн содержит целочисленный `id`, строковый `title`, дату `due_date` и логический признак `done`. Новый дедлайн получает `done: false` и идентификатор, отличный от идентификаторов сохранённых дедлайнов.

## Маршруты и условия приёмки

### Проверка живости

При запросе `GET /health` сервис отвечает кодом `200` и телом `{"status": "ok"}`.

### Создание дедлайна

При запросе `POST /deadlines` сервис принимает JSON с полями `title` и `due_date`. Поле `title` содержит строку, а `due_date` принимает дату, например `2026-10-27`. При успешном создании сервис отвечает кодом `200` и возвращает созданный дедлайн со всеми четырьмя полями.

Текущая версия принимает пустой заголовок и дату в прошлом. Для отсутствующих обязательных полей или некорректных типов и дат сервис возвращает `422`. Конкретный текст ошибки валидации зависит от версии используемых библиотек и не является отдельным условием приёмки.

### Список на сегодня

При запросе `GET /today` сервис отвечает кодом `200` и возвращает массив невыполненных дедлайнов с датой не позднее текущего дня. Просроченные дедлайны входят в список, будущие и выполненные не входят. Если подходящих дедлайнов нет, сервис возвращает пустой массив.

Текущий день определяется локальной датой процесса сервиса через `date.today()`. В настройках приложения отдельный часовой пояс не задан. Список сохраняет порядок создания подходящих дедлайнов.

### Отметка выполнения

При запросе `POST /deadlines/{deadline_id}/done` для существующего дедлайна сервис отвечает кодом `200`, выставляет `done: true` и возвращает обновлённый дедлайн. После отметки дедлайн не появляется в `GET /today`.

Повторная отметка существующего выполненного дедлайна также отвечает кодом `200` и возвращает дедлайн с `done: true`. Для отсутствующего идентификатора сервис отвечает кодом `404` и телом `{"detail": "Дедлайн не найден"}`. Некорректный тип идентификатора даёт `422`.

## Проверка реализации

Команда `make test` запускает проверки проекта. Для списка на сегодня при проверке нужны случаи прошедшей, текущей и будущей даты, а также выполненного дедлайна. Дата проверки должна быть фиксированной, чтобы результат не зависел от времени запуска. Задача на расширение проверок: GitHub Issue #2.

## Сохранение дедлайнов

Сервис хранит дедлайны в SQLite через стандартный модуль `sqlite3`, без новых зависимостей. Путь к файлу задаётся переменной окружения `DEADLINES_DB_PATH`; значение по умолчанию: `deadlines.sqlite3` в рабочем каталоге процесса. При первом запуске сервис создаёт необходимые таблицы.

Созданный дедлайн сохраняет идентификатор, заголовок, дату и признак выполнения после остановки и повторного запуска сервиса с тем же файлом. Отметка выполнения также сохраняется. После перезапуска вновь созданный дедлайн получает идентификатор, отличный от идентификаторов сохранённых дедлайнов. Поведение маршрутов и фильтрация списка на сегодня остаются такими, как описано выше.

Проверки создают отдельную базу и подтверждают сохранение данных, сохранение отметки выполнения и создание нового дедлайна после перезапуска. Команда `make test` проходит. Файл рабочей базы не включается в репозиторий. Проверка `/health` не зависит от настройки будущих уведомлений.

## Веб-страница

Минимальная страница доступна по адресу `GET /`. Пользователь вводит заголовок и дату, создаёт дедлайн, просматривает список на сегодня и отмечает дедлайн выполненным. Страница использует существующие маршруты `/deadlines`, `/today` и `/deadlines/{deadline_id}/done` без изменения их поведения.

После успешного создания страница показывает подтверждение и обновляет список. Будущий дедлайн тоже получает подтверждение, хотя в списке на сегодня не появляется. После успешной отметки выполнения список обновляется. Если в списке нет дедлайнов, страница показывает понятное пустое состояние. Если запрос не удался, страница сообщает об ошибке и позволяет повторить действие.

Проверки подтверждают доступность страницы и её основной сценарий с существующими API. Для страницы не нужны новые зависимости, роли или многопользовательский сценарий. Команда `make test` проходит.

## Следующие этапы и открытые решения

В плане курса предусмотрены напоминания и развёртывание сервиса. Требования к ним нужно уточнить до реализации и записать в спецификации условия приёмки. Сроки и содержание этапов сверяются с актуальным планом курса.

В целевом описании курса также предусмотрен понятный отказ при пустом заголовке, прошедшей дате и повторной отметке. Текущая версия принимает все три случая. До изменения поведения нужно определить коды и тела ошибок, правила для уже сохранённых просроченных дедлайнов и проверяемые условия приёмки.

Остаются открытыми целевая среда развёртывания, механизм доступа, канал и правила уведомлений. Для одного пользователя в плане курса не предусмотрены совместная работа, роли и права. Выбор механизма доступа не должен автоматически добавлять многопользовательский сценарий.

Источники текущего поведения: `README.md`, `app/main.py` и `tests/test_deadlines.py`. Описание будущих этапов опирается на план сквозного проекта курса.

## Подготовка развёртывания

Для задачи GitHub Issue #5 подготовлен вариант запуска на Linux с systemd без контейнеров. Код и окружение Python находятся в `/opt/deadline-duty/app`, данные SQLite - в отдельном каталоге `/var/lib/deadline-duty`. Сервис запускается от отдельной системной учётной записи и слушает только `127.0.0.1:8000`. Путь к базе задаётся переменной `DEADLINES_DB_PATH`.

После запуска служба отвечает на `GET /health` и позволяет пройти основной сценарий. Дедлайны и отметки сохраняются при перезапуске службы. Служба перезапускается при ошибке процесса. Команда `make test` проходит, а файл службы проверяется командой `systemd-analyze verify`.

Пока аутентификация не реализована, вариант не предполагает публичного доступа. Конкретный хост, его параметры и реальный запуск ещё не подтверждены. Для удалённой проверки используется SSH-туннель; инструкция находится в `docs/РАЗВЁРТЫВАНИЕ.md`.
