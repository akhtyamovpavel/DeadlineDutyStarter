# Запуск службы на Linux

Подготовлен пример для Linux с systemd и Python 3.12. Служба работает от отдельной учётной записи, слушает только `127.0.0.1:8000` и хранит SQLite вне каталога программы. Адрес конкретного сервера и параметры доступа ещё не определены, поэтому сам сервер не настроен.

## Подготовка каталога и учётной записи

Работаем на выбранном сервере. Для новой установки создаём каталог приложения и клонируем согласованную версию проекта. Команды рассчитаны на то, что `/opt/deadline-duty/app` ещё не существует.

```bash
sudo mkdir -p /opt/deadline-duty
sudo git clone https://github.com/akhtyamovpavel/DeadlineDutyStarter.git /opt/deadline-duty/app
cd /opt/deadline-duty/app
sudo make install
sudo make test
```

Проверяем, что учётная запись `deadline-duty` ещё не занята. Если она уже существует, не меняем её автоматически и сначала выясняем назначение. Для новой учётной записи выполняем:

```bash
getent passwd deadline-duty
sudo useradd --system --user-group --home-dir /nonexistent --shell /usr/sbin/nologin deadline-duty
```

Доступ на чтение и выполнение каталога приложения и `.venv` должен быть у системной учётной записи. Зависимости устанавливаются только в окружение проекта. Не переносим созданное виртуальное окружение в другой путь.

## Установка службы

Шаблон службы находится в `deploy/deadline-duty.service`. Он использует код из `/opt/deadline-duty/app`, а базу размещает в `/var/lib/deadline-duty/deadlines.sqlite3`. Каталог данных предназначен только для этой службы: systemd может изменить владельца существующего каталога и файлов внутри него.

При наличии `/etc/deadline-duty.env` systemd передаёт переменные из него в процесс.
Если в установленной версии настроен доступ по паролю, задаём необходимые переменные
в этом файле и ограничиваем доступ к нему: владелец `root`, права `0600`. Сам файл и
учётные данные в репозиторий не добавляем.

```bash
sudo systemd-analyze verify deploy/deadline-duty.service
sudo install -m 644 deploy/deadline-duty.service /etc/systemd/system/deadline-duty.service
sudo systemctl daemon-reload
sudo systemctl enable --now deadline-duty.service
sudo systemctl status deadline-duty.service
```

`systemd-analyze verify` проверяет файл службы, но не подтверждает доступность Python и прав кода для системной учётной записи. Успешный запуск нужно проверить отдельно.

## Проверка запуска и данных

На сервере проверяем ответ приложения и журнал службы:

```bash
curl --fail http://127.0.0.1:8000/health
sudo journalctl -u deadline-duty.service -n 50 --no-pager
```

Из браузера на своей машине можно открыть страницу через SSH-туннель, заменив адрес сервера на фактический:

```bash
ssh -L 8000:127.0.0.1:8000 SERVER
```

После подключения открываем `http://127.0.0.1:8000/`, создаём тестовый дедлайн и проверяем его в списке на сегодня. Затем перезапускаем службу через `sudo systemctl restart deadline-duty.service`, проверяем сохранность дедлайна, отмечаем его выполненным и ещё раз проверяем состояние после перезапуска.

Данные приложения хранятся отдельно от кода. Перед обновлением делаем проверенную резервную копию SQLite штатным механизмом SQLite и отдельно сохраняем предыдущую версию приложения. Совместимость будущих изменений схемы и порядок отката нужно проверять для каждого обновления.

Без настроенной аутентификации не открываем порт приложения наружу и не подключаем публичный прокси. Доступ к службе и открытие сетевого доступа требуют отдельного решения по защите.
